# 踩坑笔记

按「发现顺序」记录，每条都带定位手段与修复结论。编号前缀：
`G` = Go 移植期，`Q` = Qoder 协议/网关，`C` = Codex 接入，`R` = 仓库卫生。

## G1 · Go 的 regexp 是 RE2，不支持前瞻断言

Python 版有几处 `(?=...)`（`_CALL_TAG_LEAD_RE` 等）。直接照搬会导致
**启动即 panic**：

```
panic: regexp: Compile(`^\s*([A-Za-z_][A-Za-z0-9_.:\-]*)\s*(?=[,:=]|[({\[]|$)`):
error parsing regexp: invalid or unsupported Perl syntax: `(?=`
```

**修法**：把前瞻改写成「捕获分隔符，再由调用方裁剪」。没有别的选择——RE2 不回溯，
这是设计约束而非 bug。

**定位手段**：`go test ./internal/guards/` 会在 init 阶段就 panic，堆栈直接指向
`regexp.MustCompile`。

## G2 · `sync.Mutex` 不可重入，锁内调 Load 会死锁

Python 用 `threading.RLock`，同一线程可重复取锁。Go 的 `sync.Mutex` 不行。
路由配置的 `Save` 里再调 `Load`（都取同一把锁）→ 测试挂起 30 秒后超时：

```
github.com/xzs/bridge_qoder/internal/route.(*Manager).Load
	.../route.go:131
github.com/xzs/bridge_qoder/internal/route.(*Manager).Save
	.../route.go:423
```

**修法**：`Save` 先 `Load`、再写文件，不跨调用持锁。

**检查清单**：任何 `Lock()` 之后又调自己包内的公开方法，都要确认该方法是否也取锁。

## G3 · Windows 时钟精度 15 ms，时钟派生的 UUID 会撞号

前缀会话缓存需要给每个新前缀生成一个上游 `session_id`。第一版用
`time.Now().UnixNano()` 填充字节：

```go
now := time.Now().UnixNano()
for i := range b { b[i] = byte(now >> (uint(i%8) * 8)) }
```

两个连续调用落在同一 tick → 同一个 UUID → **两个不同会话被映射到同一个上游 session**。
测试 `TestMemoryPrefixAffinity`（「两个账号不能共用 session」）抓出来的。

**修法**：改用 `crypto/rand.Read`；失败时退到 `sha256(时钟|原子计数器)`。

**教训**：任何「唯一 ID」都不要用时钟派生，尤其是 Windows。`hash/fnv` + 计数器也不够，
并发下仍需原子性。

## G4 · LRU 只淘汰「已过期」项 → 缓存无界增长

`TestMemoryCacheLRUBound` 写入 20 条（上限 4）后断言 entries ≤ 8，实际 20。

原因：淘汰循环里加了 `if e.expires.Before(now)` 才删，未过期项永远留着。

**修法**：超上界直接淘汰最旧项，不看是否过期。

## G5 · 错误归类顺序把「本地无账号」报成「上游瞬时故障」

最初 `friendlyUpstreamError` 只按上游特征匹配，于是：

```
{"error":{"code":503,"message":"上游瞬时故障 (HTTP 503)：网关已对同账号自动重试仍失败，
 请稍后重试。上游详情：upstream HTTP 503: no usable account for realm 'cn'..."}}
```

用户会去查网络和上游，而真正原因是账号池为空。

**修法**：在函数开头先认本地前缀（`no usable account` / `API Key / routing account scope` /
`routing configuration error` / `model is only available in realm`），给出指向看板账号页的文案。

**同类问题**：错误包装改变了 `err.Error()` 的前缀，导致匹配失效。所以后来加了
`upstreamDetail(err)` 直接从 `*upstream.StatusError` 取 `Detail`，不再依赖包装后的文本。

## G6 · panic 恢复写在 `defer` 里但没有中间件包裹

`routeRequest` 里的 `defer recover()` 只能兜住同一 goroutine。SSE 流内若在
`w.Write` 后 panic，客户端拿到的是断流而非错误帧。

**结论**：守卫链设计成纯函数（`Process(frames, allowed) ([]Frame, *ToolCallError)`），
把「可能失败」的判断前移到写字节之前，减少流中途出错的概率。

## G7 · 端口 118090 越界：`--port` 报错、`PORT` 环境变量却静默回落

一次手误把默认端口从 `18090` 写成 `118090`（多了个 1）。TCP 端口上限是
65535，`118090` 根本不可能监听。

更麻烦的是三条入口行为不一致：

| 入口 | 旧行为 |
|---|---|
| `--port 118090` | 参数校验 `n > 65535` 直接报 `invalid --port` ✅ |
| `PORT=118090` | `Atoi` 成功就赋值，**不做范围检查**，随后 `net.Listen` 才失败 ❌ |
| 默认值常量 | 落在 `if cfg.Port == 0` 分支里，绕过了任何校验 ❌ |

**修法**：

1. `PORT` 环境变量走与命令行相同的 `1–65535` 校验，越界直接返回错误
   （不要静默回落到默认值——那会让进程监听在操作者没连接的端口上）。
2. 新增 `config_test.go` 的 `TestLoadConfigPort` 钉住默认值、环境变量、
   越界拒绝、命令行优先四条行为。

**教训**：同一个配置项有多条入口（flag / env / 默认值）时，校验必须收敛到
一处。三条路径各自校验，必然有一条被漏掉。

## G8 · 拆包只搬新文件、不删旧实现 → 59 个 redeclared

把协议层抽成 `internal/qoder` 时，做法是「新建包 + 在 `accounts` 里加别名桥接」，
但**忘了删 `accounts` 里的旧实现**。两边同名符号并存，编译器一次报 59 个
`X redeclared in this block`，另有 10 个类型不匹配。

分布（必须加 `-gcflags=-e` 才看得全）：

```
realm.go    34   端点常量、RealmConfig、VPC 解析、候选主机
bridge.go    9   CheckinWindowHourUTC8 / LegacyExpiryNever / Credits / Composition ...
checkin.go   6   CheckinStatus / Campaign / CampaignCode ...
quota.go     3   CreditSource / QuotaContainers / NormalizeQuotaPayload
token.go     3   DesktopClientType / DefaultDesktopVersion / DesktopVersion
login.go     2   LoginTTLSeconds / MakePKCE
scan.go      2   ScannedCredential / ScanDesktopCredentials
```

**为什么容易漏**：默认 `go build` 报满 10 条就 `too many errors` 收工，很容易
误以为「只有 9 个问题」。

```bash
cd code && go build ./...                 # 只到 10 条就截断
cd code && go build -gcflags=-e ./...     # 全量 69 条
```

**顺带暴露的类型错误**（删掉重复声明后才会真正需要处理）：

| 位置 | 错误 | 根因 |
|---|---|---|
| `bridge.go:93` | `[]qoder.Composition` 不能当 `[]Composition` 用 | 别名只对具名类型生效，切片元素不随之别名化 |
| `bridge.go:106` | `*qoder.vpcEndpoints` 未导出类型越界 | 转发函数返回了对方的私有类型 |
| `checkin.go:645` | `cannot define new methods on non-local type Campaign` | 别名不是本地类型（见 G9） |
| `realm.go:144/231` | `VPCConfigError` 从变量变成函数 | `accounts` 里留着 `= ...` 赋值与 `!= ""` 比较 |
| `scan.go:111` | `ScannedCredential` 没有 `Account` 字段 | `qoder` 版只带 `Credential`，`accounts` 版要 `Account` |

**教训**：抽包应「先删旧的、让编译红，再逐个修」。想「先加新的、保留旧的、
让两边都绿」在这个场景下不存在——同名符号不允许共存，中间态必然是红的。
这类改动**必须一次做完再提交**。

**收尾判据**：不是「新包能编译」，而是 `go build ./... && go test ./...` 同时通过。
包数会 21 → 22（新增 `internal/qoder`），但旧包里的符号数应该减少。

**后续（2026-11-17 已收尾）**：该缺陷已在提交 7aa0749 + 4b70c1b 修复——六处旧实现删除、bridge.go 成为唯一适配层（433 行）、VPCConfigError 改函数、ScannedCredential 走 accounts.AccountFromScan。go build ./... 与 go test ./... 现均通过。本节保留作过程教训。

## G9 · 别名不是本类型：不能加方法，也不能靠它换字段

`type Campaign = qoder.Campaign` 是**别名**（注意 `=`），不是新类型。两个后果：

1. 不能在 `accounts` 里写 `func (c Campaign) Label() string` —— 报
   `cannot define new methods on non-local type`。方法只能留在 `qoder` 侧，
   或改成包级函数 `func campaignLabel(c Campaign) string`。
2. 别名在「需要另一个类型」处毫无帮助。`ScannedCredential` 最典型：`qoder` 版字段是
   `Credential *Credential`，`accounts` 版要 `Account *Account`；别名做不到换字段，
   必须定义真类型再手工转换。

| 需求 | 用什么 |
|---|---|
| 只想让老调用点不改名 | 别名 `type X = pkg.X` |
| 要加方法、加字段、换语义 | 真类型 `type X struct{...}` + 转换函数 |

走真类型时容易漏一件事：**JSON 标签要重写一遍**。别名会自动继承，真类型不会。

## Q1 · 网关对「解析不了的模型名」静默按 auto 透传

这是本项目最危险的行为，必须理解。

实测（`max_tokens` 正常、模型名随便写）：

| 发送的 model | HTTP | credits |
|---|---|---|
| `Qwen3.8-Flash`（真模型） | 200 | 0.0028 |
| `qoder:Qwen3.8-Flash`（加前缀，旧版网关不认） | 200 | **0** |
| `cn:Qwen3.8-Flash`（同样不认） | 200 | **0** |
| `totally-bogus-model-xyz` | 200 | **0** |

即：**未知名字返回 200，但没有真实费用记录**，上游按 `auto` 路由。

**后果**：你既拿不到想要的模型，也看不出异常；客户端一切正常。

**修法（两层）**：
1. 网关 `catalog.StripModelPrefix` 剥掉 `qoder:` / `qoder/` / `qoder-`（大小写不敏感）。
2. 验证手段固定为「看 `usage.credits` 是否非 0」，不要只看 HTTP 200。

**重要例外（2026-11-16 实测）**：`credits` 为 None 不一定就是静默 auto。
`Qwen4-Max-Preview`（`qmodel_latest`）确认路由成功——有真实的 `completion_tokens`、
模型日志显示真实生成——但**上游对它不回报 credits**（原始 `usage` 为 `null`）。
对照其他模型（Qwen3.8-Flash 0.008 / DeepSeek-V4-Pro 0.065）均有记账。

判定改为两条并存，满足其一即认定路由成功：
- `credits` 非 0（正常记账），或
- `completion_tokens > 0` 且 `/usage/perf` 里该模型有真实生成。

**单看 credits 会把这类模型误判成「没路由到」**。

## Q2 · 官方改过名的模型，首次请求会解析失败

`qmodel_latest` 的显示名从 `Qwen3.7-Max` 改成 `Qwen4-Max-Preview`，但本地快照仍是旧名。
显示名 → key 的映射只在拉取模型清单时注册，请求先到就解析不到 → 落进 Q1 的陷阱
（`credits=None`）。

**修法**：`server.resolveModelKey` 解析失败时刷新一次模型清单（5 分钟缓存）再重试。

**验证**：修前 `Qwen4-Max-Preview` 的 `credits=None`，修后 `0.017`。

## Q3 · `max_tokens` 太小会与思考预算冲突

批量探测模型时用 `max_tokens: 1` 配 `reasoning_effort: xhigh`，上游返回：

```
The thinking_budget parameter must be a positive integer and not greater than 262144
```

不是网关缺陷，是上游对「输出预算 vs 思考预算」的约束。

**用法**：批量探测给 `max_tokens >= 16`；正常使用不会遇到。

## Q4 · 408/418 是上游把 provider 故障包装成 4xx

`_is_transient_upstream` 里 418 与 5xx 同级对待，因为上游会把内部故障包成
`418 + provider_error`。按「4xx 是客户端错」处理会误判成不可重试。

**同时**：`401/403/429` 永远不走瞬时重试路径，它们各有专门的账号处理逻辑。

## Q5 · 请求体常量错误不能被 `"Range of "` 之外的变体漏掉

上游对超限输出回 `400 invalid_parameter_error: Range of max_tokens should be [1, 131072]`。
最初匹配带引号的 `"Range of `，JSON 里若不是这个形态就漏判。

**修法**：同时匹配 `Range of `（无引号）。这类错误换号也不会成功，必须走
`IsRequestFault` 直接抛给客户端，**不冷却账号**——否则轮换会把整池冷 60 秒，
其他用户跟着吃 503。

## C1 · Codex 不按 slug 前缀选 provider（核心结论）

用真实抓包确认（`codex exec` 打到本地捕获服务器，`wire_api="responses"`）：

| 配置的 `model` | 服务端收到的 `model` |
|---|---|
| `cn:Qwen3.8-Flash` | `cn:Qwen3.8-Flash` |
| `glm-5.3` | `glm-5.3` |
| `237/Qwen3.8-27B` | `237/Qwen3.8-27B` |

**前缀原样透传，Codex 不做任何剥离，也没有「前缀→provider」映射**。
模型目录条目的结构里根本没有 provider / namespace 字段。

**推论**：
- `qoder:` 前缀必须配合「指向本网关的 provider」使用。
- 站点的 `ss` provider 不服务这些模型：实测 `qoder:Qwen3.8-Flash` 与裸名
  `Qwen3.8-Flash` 均返回 `503 model_not_found`。

## R1 · 编译产物与运行时状态必须分开忽略

编译产物（`/qoder-proxy.exe`）和运行时状态（`accounts/` `usage/` `logs/`）性质不同：
前者可重新生成，后者含**凭据**。两者都要忽略，但理由不同。

**验证**：`git status --porcelain --ignored` 应能看到这些目录以 `!!` 开头。

## R2 · 凭据被复制进工作树的风险

曾计划把 Python 版的 `accounts/` 整体复制到 `runtime/`，被安全策略拦下——因为
`runtime/` 不在 `.gitignore` 里，一次 `git add -A` 就会把真实 token 提交进去。

**做法**：
1. 复制前先 `git check-ignore -v <目标路径>` 确认命中忽略规则。
2. 只复制需要的单个文件，不整目录复制。
3. 提交前固定执行 `git diff --cached --name-only | grep -E '^(accounts|usage|logs)/'`，
   有输出就说明要撤回。

## R4 · 源码搬进 `code/` 后，`/accounts/` 这类锚点规则整体失效

**现象**：把源码从仓库根移到 `code/` 之后，`.gitignore` 里的 `/accounts/`、
`/usage/`、`/logs/` 只锚定仓库根，一条都不再命中。`git check-ignore` 查询
`code/accounts/settings.json` 返回空，`git status` 里 `?? code/` 把**两个账号文件的
access/refresh token、machine_identity.json、usage.jsonl、logs/** 全部包了进去。

此时一次 `git add -A` 就会把真实凭据提交进历史（还带着面板 `panel_session_secret`）。

**定位手段**（提交前必跑）：

```bash
git check-ignore -v code/accounts/settings.json    # 必须有输出
git add -A --dry-run | grep -E 'accounts/|usage/|logs/'   # 必须没有输出
```

**修法**：运行时目录用带路径的锚点补齐，两种前缀都写，兼容目录搬家：

```
/accounts/
/code/accounts/
```

**不要**为了省事写成无锚点的 `accounts/`：那会把源码包 `code/internal/accounts/`
一起忽略（编译器不会报错，但文件永远提交不上去）。

**教训**：移动目录后，`.gitignore` 与 `.gitattributes` 都要重新验证一遍。
锚点（前导 `/`）是路径敏感的，目录一搬就失效，而且是**静默失效**。

## R5 · 忽略 `*_test.go` 是错的：测试是源码

## R6 · `.gitattributes` 是「最后匹配者生效」，顺序错会静默失效

第一版把协议对齐文件写在前面、`*.json text eol=lf` 写在后面，结果：

```
$ git check-attr text code/assets/baseprompt.json
code/assets/baseprompt.json: text: set       # 期望 unset！
```

后置的 `*.json` 覆盖了前面的 `-text`，`baseprompt.json` 依然会被规范化。
这个失效**没有任何告警**，只有 `git check-attr` 才能看出来。

**正确顺序**（从宽到窄）：

1. 通用 `* text=auto eol=lf`
2. 具体扩展名 `*.go` / `*.json` / `*.md`
3. 例外：`*.bat text eol=crlf`
4. 最后：逐字节文件 `-text`

**验证方式**（改完必须跑）：

```bash
git check-attr -a -- code/assets/baseprompt.json   # text: unset
git check-attr -a -- code/web/dashboard.html       # eol: lf
git ls-files --eol | grep -v 'w/lf'                # 不应有 CRLF 的文本文件
```

**另一条经验**：本机全局 `core.autocrlf=true`。没有 `eol=lf` 兜底时，Windows
检出会把全部文本变成 CRLF，`git diff` 出现大量「内容无变化的改动」，把真正的
改动埋掉。

## R8 · 中文 `.bat` 写成 UTF-8 + LF：编码和行尾同时错

`cmd_bat_sh/win10_cmd/build-win10.bat` 生成时落成了 **UTF-8（无 BOM）+ 209 行全 LF**，
而 AGENTS.md 的规范是 **GB2312 无 BOM + CRLF**，脚本自己也写了 `chcp 936 >nul`。
两者混配必错：`chcp 936` 按 GB2312 解释字节，UTF-8 的三字节序列被拆散，
所有中文 `echo` / `REM` 全花。

实测（PowerShell 读原始字节）：

```
$b=[IO.File]::ReadAllBytes('...\build-win10.bat')
首三字节   : 40 65 63            # '@ec'，无 BOM
crlf=0  bareLF=209               # 全是裸 LF
非 ASCII 字符: 217 个（中文注释与 echo）
```

**关键点：`.gitattributes` 救不了这个错。** 里面写了 `*.bat text eol=crlf`，它只把行尾
换成 CRLF，**编码不会变**，仍是 UTF-8 字节。提交后行尾看着合规，运行时照样乱码，
比完全没配更迷惑。

**另一处易误判**：`chcp 65001` 配 UTF-8 文件在 Win10 上确实也能正常显示。
「我这边跑着没问题」不能当合规依据——规范选 936 是为了与既有脚本、`cmd.exe`
默认代码页和 GB2312 处理链一致，不是因为它唯一可行。

复核方法（提交前跑，别信编辑器状态栏）：

```powershell
# 1. 行尾
git ls-files --eol cmd_bat_sh/win10_cmd/build-win10.bat    # 期望 w/crlf

# 2. 编码：按 GB2312 能解出正常中文，且首三字节不是 EF BB BF
$b=[IO.File]::ReadAllBytes('...\build-win10.bat')
$gb=[Text.Encoding]::GetEncoding(936).GetString($b)
($gb -split "`n")[5]      # 期望正常中文，而不是乱码
```

**转换顺序**：先按当前真实编码解码 → 统一 `\n` → 按 GB2312 编码写回 → 再把 `\n`
换成 `\r\n`。顺序反了会二次损坏。验证必须用 `chcp 936` 的真实 cmd 窗口，
不能用 VS Code 的 UTF-8 预览。

## S1 · CORS 通配符开在管理端点上，等价于「任何网页都能导出全部账号」

这是一个真实可用的凭据窃取链路，不是理论风险。三个条件叠在一起：

1. 面板用 `X-Panel-Token` **请求头**鉴权（为了不在 localStorage 里存 API Key）。
2. `applyCORS` 用前缀匹配，`/accounts`、`/settings`、`/logs`、`/agents`、`/admin` 全部命中，
   回的是 `Access-Control-Allow-Origin: *`。
3. `/accounts/export?secrets=1 ` 返回明文 access/refresh/personal token。

于是：操作者在浏览器里打开面板（拿到 token，存在内存/JS 变量中），随后访问任意攻击者页面，
该页用 `fetch('http://127.0.0.1:18090/accounts/export?secrets=1', {headers:{'X-Panel-Token': ...}}) `
就能读到响应体。**注意这里不需要知道 token**：真正的利用方式是诱导面板用户点击链接后，
由同源页面或 XSS 组合完成；而更常见的是「浏览器扩展 / 本地恶意程序读到 CORS 允许的响应」。
更关键的是：**头部鉴权没有 Cookie 的 SameSite 保护**，一旦管理面允许跨域，浏览器就不再是边界。

**修法**：把 CORS 从「前缀黑名单」改成「精确允许列表」，只留推理端点与公开探活：

```
allow := []string{
    "/v1/chat/completions", "/v1/responses", "/v1/messages",
    "/v1/models", "/v1/usage", "/models", "/messages",
}
// 公开探活
if path in {"/ping","/healthz","/livez","/readyz","/health"} { allow }
```

**回归测试** `TestCORSDoesNotOpenManagementRoutes` 覆盖 16 个管理端点。它的价值在于
「新增管理路由时不会自动获得 CORS」——用允许列表而不是黑名单，才能保证这一点。

## S2 · 默认口令 + 无频率限制 = 秒级爆破

面板默认口令是 `admin`，TTL 7 天，token 是自校验签名（重启后仍有效）。`/panel/login`
原本没有任何限速，局域网里跑一个字典就能登录，然后 `/accounts/export?secrets=1 ` 一次拿走全部凭据。

**修法**：`loginThrottle`，按 `RemoteAddr` 计数。

| 失败次数 | 冷却 |
|---|---|
| 1–5 | 无（容忍手抖） |
| 6 | 30s |
| 7 | 60s |
| … | 翻倍，上限 15 分钟 |

两个设计决定：

- **不信任 `X-Forwarded-For`**。信任它等于让攻击者轮换该头绕过限速。反向代理部署应在边缘自己限速。
- **锁定期间正确口令也返回 429**。否则「200 vs 429」本身就是口令是否正确的旁路。

**测试**：`TestPanelLoginLockout`（第 6 次 429、锁定期正确口令也 429）、
`TestPanelLoginLockoutIsPerClient`（一个 IP 被锁不影响其他）、`TestThrottleBackoffGrows`、
`TestThrottleExpiresAfterCooldown`。

## S3 · 日志是凭据的第二个出口

排查上游问题时经常把错误体和 URL 原样打进日志：`model discovery failed on <url>: <err>`。
这些字符串可能带 `Bearer ...`、`T?token=...` 或整段账号 JSON。而 `/logs` 与
`/logs/export` 对**任何**面板会话可读——一个日志行就把 token 交出去了。

**修法**：脱敏放在 `logx.Logger.Log` 里，而不是各个调用点。原因是三个 sink（文件 / stderr /
内存环）都从这一个函数出去，新加的日志行无法绕过。`/logs/export` 再洗一次磁盘文件，
因为**修复前**写下的日志可能已经含 token。

**验证**（本机现有日志，修复后）：

```
Select-String logs\qoder-proxy.log -Pattern 'dt-|drt-|Bearer |accessToken'  → 0 命中
```

**测试**：`TestRedactCredentials`（9 种形态）、`TestLogRedactsBeforeEverySink`（三个 sink 都断言）、
`TestRedactLeavesOrdinaryTextAlone`（普通行不被改写）。

## S4 · Windows 上 `0o600` 是「建议值」，账号文件对全机可读

Go 的 `os.WriteFile(path, data, 0o600)` 在 Windows 上**不设置 ACL**，文件继承父目录的访问控制。
实测本机仓库：

```
> icacls code\accounts\01a1df2a-....json
BUILTIN\Administrators:(I)(F)
NT AUTHORITY\SYSTEM:(I)(F)
NT AUTHORITY\Authenticated Users:(I)(M)   <- 任何已认证进程可改
BUILTIN\Users:(I)(RX)                     <- 其他本地账号可读
```

**修法**：`icacls` 显式重建 ACL。本项目零依赖（go.mod 无 require），所以不用
`golang.org/x/sys/windows`，直接用系统自带的 icacls。

### 两个必须知道的坑

**坑 1：`/inheritance:r ` 只删继承的 ACE，保留显式的。**

我第一版只用了 `/inheritance:r `，测试直接失败：

```
accounts dir is still shared:
  ... BUILTIN\Users:(OI)(CI)(R)     <- 显式 ACE，/inheritance:r 不动它
```

实测确认：

```
icacls $d /grant '*S-1-5-32-545:(OI)(CI)R'    # 显式授权
icacls $d /inheritance:r                     # 只删继承项
icacls $d                                     # Users:(OI)(CI)(R) 仍在
```

所以必须额外 `/remove:g` 掉 Everyone（S-1-1-0）、Authenticated Users（S-1-5-11）、
BUILTIN\Users（S-1-5-32-545）。用 SID 而不是名称，才能在中英文系统上都成立。

**坑 2：目录也必须收紧。** 只改文件时，父目录的继承规则会给之后新建的账号文件重新授权。
`NewPool` 启动时会调用 `hardenCredentialPath(dir, true)` 收紧目录。

**测试的关键设计**：`t.TempDir() ` 在 Windows 上创建的就是 owner-only ACL（Go 特意这么做），
所以「文件不可读」的断言会因为**环境**而不是**修复**而通过。测试因此：

1. 在 temp 下建一个子目录，显式 `icacls /grant '*S-1-5-32-545:(OI)(CI)R' `；
2. 先用普通 `os.WriteFile` 写一个 control 文件，断言它**确实**能被 Users 读；
3. 再断言经过 `writeJSONAtomic` 的文件读不到。

没有第 2 步，这个测试就是个摆设。

**验证（真实目录）**：启动网关后，

```
> icacls code\accounts
accounts BUILTIN\Administrators:(OI)(CI)(F)
         NT AUTHORITY\SYSTEM:(OI)(CI)(F)
         DESKTOP-XXX\xzs:(OI)(CI)(F)
```

账号文件与 `settings.json` 同样只剩这三条。

## S5 · 签到「接口未开放」不是接口问题，是走错了路

**现象**：面板点「签到」，日志永远是
`本区域未开放 /sash/api/v1/me/daily-check-in 接口（HTTP 404）：每日领取活动改由官方客户端承接`，
积分从未增加。

**误导点**：这条文案把「我们调错了接口」说成「官方挪走了接口」，读起来像是无解，
于是这个功能坏了很久没人再查。

**真相**：官方确实换了机制——从 sash 的 daily-check-in 换成了**活动平台**
（`/sash/api/v1/me/campaigns` 列表 + `/sash/api/v1/me/campaigns/{id}/claim` 领取）。
Python 版 `qoder_tasks.run_checkin` 的顺序是「活动平台为主、旧 sash 兜底」，
Go 版移植时只写了兜底那一半，主路径整个缺失。

**定位方法**（可复用）：

1. 先在源仓库搜「签到」而不是搜接口名：
  ```
  rg -n 'def run_checkin|def campaign_checkin' D:/github/qoder2api-hub/*.py
  ```
2. 读它的注释，Python 版把「为什么先走活动平台」写在了 docstring 里：
  「活动平台（campaign-checkin）：当前『每日领取 100 Credits』等限时活动的真实入口」。
3. 再回到 Go 侧搜同一个概念，确认只有 `CheckinStatusFor`，没有 `CampaignCheckin`。

**修法**：新增 `CampaignCheckin`，`Checkin` 改为「先活动平台、失败才兜底」。

**教训**：移植一个功能时，要对照源实现的**调用顺序**，而不只是把它调用的接口翻译一遍。
只翻译被调用的那一半，缺失的是决策逻辑，编译器不会报错，测试也不会失败（因为没有测试）。

## S6 · 活动平台签到的四个「看起来能跑但是错的」细节

这些细节全部来自源仓库的注释与 issue 编号，逐条都容易写错，
而且写错之后**不会报错**，只会悄悄少领或重复领。

### (1) 分类必须先于 actionType 过滤

官方在领取成功后会把这个活动的 `actionType` 从 `CLAIM_BENEFIT` 降级成 `VIEW_DETAILS`。
于是「今日已领」的活动，看起来像「详情类活动」。

```
// 错：先过滤 actionType，已领的就被当成详情类丢掉了
if c.ActionType != "CLAIM_BENEFIT" { continue }
if c.ClaimStatus == "CLAIMED" { already = append(already, c) }   // 永远走不到
```

正确顺序是**先判 CLAIMED 并归类**，再对「未领」的做 actionType 过滤：

```
if c.ClaimStatus == "CLAIMED" {
    if c.Benefit.Amount > 0 || c.ActionType == "" || c.ActionType == "CLAIM_BENEFIT" {
        already = append(already, label)   // 有奖励 = 真签到过
    }
    continue                                // 详情类无奖励，不计入已领
}
if c.ActionType != "" && c.ActionType != "CLAIM_BENEFIT" { continue }
```

判定用「有奖励金额」而不是「actionType 是什么」，因为后者会被官方改写。

### (2) 空列表必须重试

源仓库 issue #130：上游偶发返回「没有每日活动 / claimable=false」，实测约 10 次有 2 次。
一次空结果就放弃，等于当天直接丢奖励。

**修法**：只在「查询成功但无可领项」时重试两次（0.8s、2.0s 退避）；
查询失败不在这里重试（那是另一条错误路径，重试只会叠加延迟）。

```
func campaignListNeedsRetry(st *CampaignView, onlyCredits bool) bool {
    if st == nil || !st.OK { return false }        // 失败走错误路径
    if len(st.Campaigns) == 0 { return true }
    if !st.Show && !st.Claimable { return true }
    // 有任一 CLAIMABLE 且属于本次范围 -> 不用重试
}
```

### (3) 同人去重是「按人」不是「按号」

单账号池也会收到 `SAME_PERSON_ALREADY_CLAIMED`：上游按机器身份去重，
同一台设备的其他账号领过了，这个号也会被拒。

这**不是**账号坏了，但每天重试只会重复被拒。正确处理是：

1. 记 6 小时冷却（`campaignBlockedUntil`，复用已有字段）；
2. 盖上本地签到章，避免调度器每轮都打上游；
3. 在结果里如实说明「同人已领取」，而不是报「失败」。

### (4) gap=0 是合法值，不要 clamp

`gap` 是相邻两次 claim 的间隔。调用方传 0 表示「不要等」（测试、手工排查），
传 1.0 是调度器的防风控默认。如果用 `if gap <= 0 { gap = 1.0 }` 去兜底，
就永远无法表达「不等」，测试会被拖慢，也无法验证批量逻辑。

正确写法是只处理负数：

```
if gap < 0 { gap = 0 }
// gap == 0 时不 sleep
```

**测试**：`TestCampaignCheckinGapIsHonoured` 用两个可领活动 + gap=0 断言耗时 < 900ms。

## S7 · 兜底路径要判「有没有结论」，不是判「成功与否」

签到改成双路径后，最容易写错的边界是：**活动平台成功但没东西可领**时，
还要不要去调旧接口？

如果按 `if camp.OK` 判断，就会继续走旧接口，于是一个账号可能被两套机制各领一次，
或者至少白白多打两次上游请求。

**正确判据**是「这次活动平台有没有给出结论」：领到了、已领过、被同人去重、
名额发完、成就未完成、或者明确说「无可领活动」——这些都算结论，不该再兜底。
只有「活动列表取不到」才兜底。

```
func campaignHasConclusion(res *CampaignCheckinResult) bool {
    if res == nil { return false }
    return len(res.Claimed) > 0 || len(res.Already) > 0 ||
        len(res.Blocked) > 0 || len(res.Pending) > 0 ||
        len(res.Locked) > 0 || res.Message != ""
}
```

**测试**：`TestCheckinDoesNotConsultLegacyWhenCampaignsAnswer` 用计数器断言旧接口被调用 0 次。

写这个测试时踩到一个次生坑：第一次断言失败，报「legacy 被调用 7 次」。
排查发现不是代码问题，而是**测试把配额刷新扫到的路径也算进去了**——
`refreshCreditsQuietly` 会遍历 ` CreditPaths ` 探测配额接口，我的假上游把所有未识别路径都计数了。
改成只统计 `/daily-check-in/status` 与 `/daily-check-in/claim` 两条即可。
**教训**：假上游的「默认分支」不要用来计错误，否则任何无关探测都会被算进去。
