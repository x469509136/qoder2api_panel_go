## 0.1 `go build ./...` 报 `redeclared in this block`（历史案例，已修复）

**现状**：该缺陷已在提交 `7aa0749` + `4b70c1b` 修复，当前 HEAD `go build ./...` 通过。
以下内容保留作历史排查参考——如果将来再遇到同类报错，思路仍然适用。

**当年的症状**：`cd code && go build ./...` 在 `internal/accounts` 上报一串
`X redeclared in this block`，末尾 `too many errors`（默认截到 10 条，
`go build -gcflags=-e ./...` 才能看到全部 69 条）。

**根因**：拆包只搬了新文件、没删旧实现——`internal/qoder` 已把实现搬走，
`accounts` 里的旧实现还在，`bridge.go` 又声明了一遍（详见《踩坑笔记》G8/G9）。

**当时的处置**：

| 目标 | 命令 |
|---|---|
| 只想跑起来 | `git stash -u` 暂存拆包改动，回到上一个可编译提交 |
| 只想验证新协议包 | `go build ./internal/qoder` / `go test ./internal/qoder` |
| 收尾拆包 | 删除旧实现，判据是 `go build ./... && go test ./...` 同时通过 |

**教训**：同名符号不允许共存，「两边都留着让它绿」的中间态不存在。
抽包应「先删旧的、让编译红，再逐个修」，一次做完再提交。

## 1. 启动相关

### 1.1 端口被占用

```
[ERROR] failed to listen on 127.0.0.1:18090
```

如果是启动就报 `invalid --port` 或 `invalid PORT`，那是**配置值越界**（端口上限
65535），不是占用。例如把 18090 误写成 118090。

先确认占用者是谁，再决定是否停：

```bash
netstat -ano | grep LISTENING | grep ":18090"
wmic process where "ProcessId=<PID>" get ProcessId,CommandLine /format:list
```

若占用者是另一个 `qoder-proxy`，说明已经跑了一份——不要再起第二个（同一个
`accounts/` 目录两个进程会竞争 token 刷新，见踩坑笔记 Q6）。

端口来源优先级：`--port` > `PORT` 环境变量 > 默认 18090。排查「明明配了端口却在
别的端口监听」时，先确认环境变量有没有被 shell/服务配置覆盖：

```bash
echo "$PORT"          # bash
$env:PORT            # PowerShell
```

### 1.2 打印「已有一个反代在运行」后退出

这是**预期行为**：启动时探测到已有 `qoder-proxy` 应答，直接退出 0。
要重启就先停掉旧进程（`stop-qoder-proxy.bat` 或 `taskkill`）。

### 1.3 `assets/` 或 `web/` 找不到

`baseprompt.json` 与双区模型快照已 `go:embed`，缺失外部文件会自动回退；
但 `dashboard.html` 与 `i18n/` **不打进二进制**，需要在可执行文件同级目录
（或工作目录）存在。

验证：

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18090/     # 200
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18090/i18n/en.json  # 200
```

---

### 1.4 构建脚本产物落到哪里 / `dist-win/` 为什么没被忽略

`cmd_bat_sh/win10_cmd/build-win10.bat` 默认输出到 `<repo>\dist-win`，可用 `OUT_DIR`
覆盖：

```bat
cmd_bat_sh\win10_cmd\build-win10.bat              REM 构建 release
cmd_bat_sh\win10_cmd\build-win10.bat debug        REM 带符号
cmd_bat_sh\win10_cmd\build-win10.bat clean        REM 先停服再删产物目录
set OUT_DIR=D:\tmp\qoder-build && cmd_bat_sh\win10_cmd\build-win10.bat
```

产物目录里是：`qoder-proxy.exe`、`web/ i18n/ assets/` 的副本、`SHA256SUMS.txt`、
以及空的 `accounts/ usage/ logs/`。这些**全部可再生**，已进忽略清单
（`/dist-win/`、`/code/dist-win/`）。确认：

```bash
git check-ignore -v dist-win/SHA256SUMS.txt   # 命中 /dist-win/ 即正常
git status --short                            # 不该出现 dist-win/
```

**若 `clean` 报 `stop-win10.bat` 找不到**：这是脚本的设计缺口，不是你的环境坏了。
当前目录只有 `build-win10.bat`，`clean` 分支的 `call "%~dp0stop-win10.bat" quiet`
会失败一次（不中断），随后照常删 `OUT_DIR`。要真正停服请手动：

```powershell
Get-Process qoder-proxy -ErrorAction SilentlyContinue | Stop-Process -Force
```

**若中文全是乱码**：脚本当前是 UTF-8 编码，而 `chcp 936` 按 GB2312 解释，见
《踩坑笔记》R8。临时绕过：把脚本另存为 GB2312 无 BOM + CRLF，或在支持的编辑器里
以 `chcp 65001` 运行。

## 2. 鉴权相关

### 2.1 401 `panel password required`

管理类端点（`/accounts` `/usage` `/settings` `/logs` `/diag` `/admin` `/tasks`）
需要面板会话。先登录拿 token：

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:18090/panel/login \
  -H 'Content-Type: application/json' -d '{"password":"admin"}' \
  | sed 's/.*"token":"\([^"]*\)".*/\1/')
curl -s http://127.0.0.1:18090/accounts -H "X-Panel-Token: $TOKEN"
```

### 2.2 401 `invalid api key`

推理端点有 Key 时不接受空 Key。Key 可从以下任一处传：
`Authorization: Bearer`、`x-api-key`（Anthropic 客户端）、`?key=`。

`/panel/status` 的 `api_key_set` 为 `true` 时表示必须带 Key。

### 2.3 面板口令忘了

`accounts/settings.json` 里的口令是 PBKDF2 摘要，不可逆。重置：

```bash
# 停进程后删除口令相关字段（文件里其余配置保留）
python -c "
import json,os
p=r'<accounts-dir>/settings.json'
d=json.load(open(p,encoding='utf-8'))
for k in ('panel_password_hash','panel_password_salt','panel_password_rounds'):
    d.pop(k,None)
d['panel_password_default']=True
json.dump(d,open(p,'w',encoding='utf-8'),ensure_ascii=False,indent=2)
"
```

或者用首选方式：启动时 `--panel-password <新口令>`。

### 2.4 `/settings/reveal` 返回 403

**预期行为**：面板还在默认口令 `admin` 时不允许显示明文 Key。先改口令。

### 2.5 `/accounts/export` 导出的 JSON 里没有 token

**2026-11-16 起是预期行为**：默认剥离 `accessToken` / `refreshToken` /
`personalToken`，避免默认口令 `admin` 下被顺手导走凭据。

跨实例迁移或备份时显式要明文：

```bash
curl -s 'http://127.0.0.1:18090/accounts/export?secrets=1' \
  -H "X-Panel-Token: $TOKEN" -o accounts-backup.json
```

看板上的「导出 / 导出单个」按钮已经自动带 `?secrets=1`，点按钮不受影响。

若确实拿不到 token，检查是否漏了 `secrets=1`（大小写敏感，只认字符串 `1`）。

### 2.6 `/health` 里没有 `uid` / `domain`

**2026-11-16 起是预期行为**。账号身份只对三种来源可见：

1. 有效面板会话（`X-Panel-Token`）；
2. 有效 API Key；
3. 回环地址（本机 `127.0.0.1` / `::1`）。

远程 + 未配 Key 时只返回匿名快照（`ok` / `version` / 账号数等）。这是为了修掉
"`--host 0.0.0.0` 且未配 Key 时局域网可读到当前账号 uid" 的问题。

排查时想看到 uid，带面板 token 即可：

```bash
curl -s http://127.0.0.1:18090/health -H "X-Panel-Token: $TOKEN" | head -c 400
```

## 3. 推理失败

排查顺序：**模型名 → 账号 → 出口区域 → 额度**。

### 3.1 503 `网关没有可用账号`

```bash
TOKEN=...  # 见 2.1
curl -s http://127.0.0.1:18090/accounts -H "X-Panel-Token: $TOKEN" | head -c 600
```

看每个账号的 `enabled`、`cooldown_left_s`、`expires_at`、`guardrails.blocked`。
常见原因：凭证过期（`lastError` 含 `TOKEN_EXPIRE`）、余额地板护栏触发、
当日 token/积分上限。

### 3.2 400 `模型 X 已被本机网关封禁`

`accounts/settings.json` 的 `banned_models` 命中了。看板「设置」里调整，或：

```bash
curl -s -X POST http://127.0.0.1:18090/settings/save -H "X-Panel-Token: $TOKEN" \
  -H 'Content-Type: application/json' -d '{"banned_models":[]}'
```

### 3.3 400 `跨区错配`（模型只在另一个区域提供）

模型有区域独占（如 CN 的 `q37fmodel`、INTL 的 `ultimate`），而 Key 绑定的是另一区。
改用对应出口的 Key，或把 Key 出口改为「跟随面板切换」。

### 3.4 请求返回 200 但内容不对 / 像是别的模型答的

**这是最需要警惕的一类**。网关对解析不了的模型名会原样透传给上游，上游按 `auto`
路由并返回 200，`usage.credits` 为 0。

判定方法（唯一可靠）：

```bash
tail -5 usage/usage.jsonl | python -c "
import sys,json
for l in sys.stdin:
    d=json.loads(l); print(d.get('model'), 'credit=', d.get('credit'))
"
```

- `credit` 非 0 → 真的打到了目标模型
- `credit` 为 0 或缺失 → 落进了 auto 透传

常见触发：模型名拼错、带不规范前缀（如 `cn:` 发给本网关）、官方改过名但快照未更新。

### 3.5 502 `工具调用参数不是合法 JSON`

上游把工具调用吐成了正文且参数坏掉，网关按协议 fail-closed。这**不是**客户端问题，
重试该轮即可。若频繁出现，可在设置里把 `tool_echo_mode` 改为 `lenient`
（代价：客户端不知道残片被丢弃）。

观察计数：`/usage/perf` 的 `tool_guards`。

### 3.6 流式中断 / 客户端一直重连

1. 看 `logs/qoder-proxy.log` 是否有 `tool-echo guard failed`。
2. 确认不是上游首字超时：`/usage/perf` 的 `ttft.p99`。
3. 网关每 5 秒发 SSE 注释 `: ping` 保活；若客户端仍断，多半是中间代理的空闲超时，
   调大客户端侧超时。

## 4. 额度与用量

### 4.1 余额显示 0 但官方客户端有额度

先跑端点探测（INTL 的额度路径与 CN 不同）：

```bash
curl -s -X POST http://127.0.0.1:18090/credits/probe -H "X-Panel-Token: $TOKEN" \
  -H 'Content-Type: application/json' -d '{"limit":6}'
```

命中后会记到 `accounts/credits-source.json`，后续优先使用。

### 4.2 余额被写成「未知」

上游对失效凭证会回全 0 的退化体。网关会标成「未知」而不是 0，避免误触发护栏、
误停账号。等下一次成功刷新即恢复。

### 4.3 缓存命中率突然变 0

按顺序查：

1. `/usage/stats` 的 `full_price`：超长 prompt + 0 命中会被单独计数。
2. 会话亲和是否被打断：`/usage/recent` 里同一对话的 `account` 是否变化。
3. `upstream_session_id` 是否每轮都变（前缀缓存开关 `QD_SESSION_CACHE`）。
4. 客户端是否把 system prompt 写成了每轮变化的内容（会从第 0 字节就匹配失败）。

## 5. 签到与调度

### 5.1 签到「无效」

```bash
curl -s -X POST http://127.0.0.1:18090/diag/checkin -H "X-Panel-Token: $TOKEN" \
  -H 'Content-Type: application/json' -d '{}'
```

看每个账号的 `status` / `unavailable` / `reason`。INTL 的旧签到接口常年 404，
应走活动平台（`/tasks`）。

### 5.1.1 签到显示「本区域未开放 /sash/.../daily-check-in」

**2026-11-17 之前是预期内的错误**：Go 版只调了旧 sash 接口，而官方早已改用活动平台。
现在主路径是活动平台，如果仍看到这条文案，说明**活动平台也取不到列表**，才轮到
旧接口报 404。按顺序查：

```
# 1. 直接看活动列表能不能取到（需要面板 token）
curl -s http://127.0.0.1:18090/agents/models?realm=cn -H "X-Panel-Token: $TOKEN" >/dev/null
curl -s -X POST http://127.0.0.1:18090/accounts/checkin \
  -H "X-Panel-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"uid":"<uid>"}' | head -c 800
```

看返回的 `campaign` 字段：

| 现象 | 含义 | 下一步 |
|---|---|---|
| `error` 含 `campaign list unavailable` | 活动列表取不到 | 查出口 IP / 401 / 网络；看 `logs` 的 `campaigns` |
| `claimed` 有值 | 本次真的领到了 | 看 `credits_remain` 是否增加 |
| `already` 有值 | 今天已领过 | 正常，不用处理 |
| `blocked` 有值 | 同一设备其它账号已领（按人去重） | 正常，换号也没用 |
| `pending` 有值 | 名额发完 | 次日 10:00（UTC+8）后重试 |
| `locked` 有值 | 成就不够 | 需先在官方桌面端完成新人任务 |

### 5.1.2 签到「成功」但积分没涨

活动平台的积分发放有秒级延迟，且网关会在领取后刷新余额。若仍看不到：

1. 确认不是 `creditsNone` 这类「上游不回报余额」的情形（见《踩坑笔记》Q1）。
2. 看 `/accounts` 里该账号的 `lastCheckin` 是否是今天（本地盖章只在成功后写）。
3. 用官方桌面端打开权益中心核对——上游按「人」去重，客户端可能已经领过。

### 5.1.3 批量签到结果里 `already` / `blocked` 有数但 `credit_added` 是 0

**这是正确行为**，两个计数是 2026-11-17 新增的语义：

| 字段 | 含义 | 是否算失败 |
|---|---|---|
| `already` | 今日已领取 | 否 |
| `blocked` | 被上游按人去重 | 否 |
| `failed` | 真正失败（上游报错 / 网络） | 是 |

三者互斥，只有 `failed` 大于 0 才需要处理。

```bash
curl -s http://127.0.0.1:18090/scheduler -H "X-Panel-Token: $TOKEN" \
  | python -c "import sys,json;d=json.load(sys.stdin);print(d['enabled'],d['next_run_time'],d['last_run_time'])"
```

- `enabled=false` → `POST /scheduler/toggle {"enabled":true}`，或改
  `accounts/scheduler/state.json`。
- `next_run_time` 为空 → cron 表达式非法（启动时会打日志并忽略）。

## 6. Codex 接入

### 6.1 Codex 报 `503 model_not_found` / `No available channel`

说明请求发到了不服务该模型的 provider。确认当前 provider：

```bash
# 看这次执行用的是哪个 provider
codex --profile qoder exec --skip-git-repo-check "hi" 2>&1 | head -12
# 输出里有 provider: qoder / model: qoder:Qwen3.8-Flash
```

`qoder:` 前缀的模型必须走 `qoder` provider（`http://127.0.0.1:18090/v1`）。
走默认的 `ss`（station）会 503 —— 那不是网关问题。

### 6.2 Codex 报 `--profile` 冲突

```
legacy `profile = "qoder"` or `[profiles.qoder]` config
```

0.167 起 profile 必须放在独立文件。主 `config.toml` 只能有
`[model_providers.qoder]`，profile 内容放到 `qoder.config.toml`。

### 6.3 改了 `bridge_models.json` 但 Codex 没变化

```bash
CODEX="C:/Users/xzs/AppData/Local/OpenAI/Codex/bin/9e1da79431da526b/codex.exe"
"$CODEX" debug models > /tmp/eff.json && python -c "
import json;d=json.load(open('/tmp/eff.json',encoding='utf-8'))
print(len(d['models']),'models parsed')
"
```

- 报 `missing field xxx` → 缺必填字段，**整个文件**都不会加载（没有逐条容错）。
- 能解析但找不到某条 → 检查 `visibility` 是否 `list`、`supported_in_api` 是否 `true`。

### 6.4 想确认某个模型是不是真在工作

唯一可靠的标准是网关侧有非 0 计费：

```bash
curl -s -X POST http://127.0.0.1:18090/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qoder:Qwen3.8-Flash","max_tokens":16,
       "messages":[{"role":"user","content":"hi"}]}' | python -c "
import sys,json;d=json.load(sys.stdin)
print('credits =', (d.get('usage') or {}).get('credits'))
"
```

`credits` 为 0 或 `None` 就是没真正路由到。

## 7. 时钟与环境自检

`/health` 的 `env` 段：

| 字段 | 含义 | 异常后果 |
|---|---|---|
| `clock_skew_s` | 与上游的时钟偏差（秒） | 超过 ±120 秒，COSY 签名直接 401 |
| `accounts_writable` | `accounts/` 是否可写 | 不可写则设备身份无法持久，容器重建等于换设备 |
| `identity_cached` | 机器身份是否已缓存 | false 时签到链路不发机器头 |
| `container` | 是否在容器内 | 容器 + INTL 账号容易被上游限流 |
| `proxy` | 是否配置出口代理 | 影响上游连通性 |

时钟漂移的处理：容器内需要宿主机时间同步；Windows 上 `w32tm /resync`。
